# WebLed2.0 REST API

HTTP-эндпоинты, которые отдаёт ESP32-S3 (HTTP, порт 80; при `CONFIG_SERVER_HTTPS` — HTTPS, порт 443).

Машиночитаемая спецификация (OpenAPI 3) — [openapi.yaml](openapi.yaml): импортируется в Postman,
Insomnia, Swagger Editor.

Базовый URL в примерах: `http://<ip-esp>` (например `http://192.168.0.50`).
Хендлеры регистрируются в четырёх местах:

- `components/device/src/device.cpp` — `/api/device`, `/api/led`, `/api/file`
- `components/wifi_manager/src/wifimanager.cpp` — `/api/network`
- `components/server/src/ota.cpp` — `/api/ota/*`
- `components/server/src/server.cpp` — `/` (веб-страница для теста)

Успешные ответы — JSON с `Content-Type: application/json`.
Ошибки парсинга/валидации запроса — `400`/`404`/`500` с **plain text** телом (`httpd_resp_send_err`).
Логические ошибки часто приходят как `200` + `{"status": false, "error": "..."}` — смотрите на поле `status`, а не только на код.

### Query-параметры

Для GET с query (`?info`, `?state`, …) проверяется только **наличие** ключа — значение не важно, но
`httpd_query_key_value` требует `=`: используйте `?info=` или `?info=1`.
Если нужного параметра нет — `404 Query param is missing`.

Вся query-строка читается в буфер 128 байт (`get_query_param` в `helper_server.cpp`) —
длинные имена файлов обрежутся.

### Тело POST

`getjson()` (`helper_server.cpp`): тело обязательно, размер < 8192 байт.

| Код | Тело ответа |
|-----|-------------|
| 400 | `Empty body` |
| 400 | `Body too large` — тело ≥ 8192 байт |
| 400 | `Recv failed` |
| 400 | `Invalid JSON` |
| 500 | `OOM` |

## `GET /`

Тестовая панель — одна HTML-страница, встроенная в прошивку (`components/server/web/index.html`).
Дёргает все эндпоинты ниже, кроме OTA.

Страница встраивается **сжатой gzip** (~117 КБ → ~32 КБ) и отдаётся с `Content-Encoding: gzip`.
Сжатие делается само при сборке, если `index.html` изменился (`components/server/web/gzip_page.py`,
правило в `components/server/CMakeLists.txt`). Править нужно только `index.html`.

## `GET /api/led`

### Ответ

```json
{
  "settings": {
    "led_count": 60,        // количество светодиодов
    "save_mode": true,      // сохранять ли состояние в NVS
    "manual":    false,     // ручное управление (автоматика заблокирована)
    "led_model": "ws2812",  // тип ленты: "ws2812" | "ws2815"
    "pixel_format": "grb"   // порядок цветов: "grb" | "rgb"
  },
  "state": {
    "speed":      50,       // 0..100
    "mode":       254,
    "brightness": 80,       // 0..100
    "color": { "r": 255, "g": 64, "b": 0 }
  },
  "modes": [
    { "id_mode": 1,   "name": "Радуга" },
    { "id_mode": 2,   "name": "Бегущий огонь" },
    { "id_mode": 3,   "name": "Огонь" },
    { "id_mode": 4,   "name": "Дыхание" },
    { "id_mode": 5,   "name": "Мерцание" },
    { "id_mode": 6,   "name": "Погоня" },
    { "id_mode": 7,   "name": "Волна" },
    { "id_mode": 8,   "name": "Заполнение" },
    { "id_mode": 9,   "name": "Сканер" },
    { "id_mode": 253, "name": "Ручной" },
    { "id_mode": 254, "name": "Статичный цвет" },
    { "id_mode": 255, "name": "Выкл" }
  ]
}
```

`modes` отсортирован по `id_mode`. Встроенные эффекты — `components/led/led_effects.cpp`,
к ним добавляются скрипты, загруженные через `POST /api/file` (со своим `id`).
Id 1–9 и 253–255 заняты встроенными эффектами — скриптам нужен id от 10.

Анимации 2–9 берут цвет из `state.color`, а скорость из `state.speed` (0 — медленно, 100 — быстро);
«Огонь» использует цвет как оттенок пламени (тёмный → цвет → белый).

## `POST /api/led`

Все секции опциональны. Отсутствующее поле = без изменений.

```json
{
  "settings": {
    "manual":    true,      // bool — вкл/выкл ручное управление
    "led_count": 60,        // число > 0, сохраняется в NVS
    "save_mode": true,      // bool
    "led_model": "ws2815",  // "ws2812" | "ws2815" — лента пересоздаётся сразу, без перезагрузки
    "pixel_format": "rgb"   // "grb" | "rgb" — можно передать только одно из двух полей
  },
  "state": {
    "mode":       254,      // игнорируется, если такого id нет в modes
    "speed":      50,       // 0..100
    "brightness": 80,       // 0..100
    "color": { "r": 255, "g": 0, "b": 0 }   // применяется только при всех трёх r/g/b
  },
  "leds_arr": [             // попиксельно; включает режим 253 "Ручной"
    { "id": 0, "color": { "r": 255, "g": 0, "b": 0 } },
    { "id": 1, "color": { "r": 0, "g": 255, "b": 0 } }
  ]
}
```

### Порядок обработки

1. `settings.manual` применяется первым — в одном запросе можно включить ручной режим и сразу поменять ленту.
2. `settings.led_count` / `settings.save_mode` / `settings.led_model` / `settings.pixel_format` применяются
   **всегда**, даже если запрос заблокирован (п. 3). Тип ленты и порядок цветов хранятся в NVS (`led_model`,
   `px_format`); на устройствах без этих ключей — WS2812 + GRB. Неизвестное значение игнорируется (лог).
3. Если в запросе есть `state` или `leds_arr`, есть хотя бы одна автоматика и ручной режим выключен —
   `state`/`leds_arr` **не применяются**, ответ `409`.
4. `state` применяется одним вызовом `set_state` (одна запись в NVS).
5. `leds_arr`: элементы без числового `id` или без полного `color` пропускаются;
   `id >= led_count` игнорируется (лог на устройстве).

### Ответы

| Код | Тело |
|-----|------|
| 200 | `{"status": true}` |
| 409 | `{"status": false, "error": "работает автоматика. Включите ручное управление"}` |
| 400 | см. «Тело POST» |

Неизвестный `mode` **не** даёт ошибку — поле просто игнорируется.

### Примеры

```bash
# Включить ручной режим и поставить статичный красный
curl -X POST http://192.168.0.50/api/led -H 'Content-Type: application/json' \
  -d '{"settings":{"manual":true},"state":{"mode":254,"color":{"r":255,"g":0,"b":0}}}'

# Вернуть управление автоматике
curl -X POST http://192.168.0.50/api/led -H 'Content-Type: application/json' \
  -d '{"settings":{"manual":false}}'
```

## `GET /api/device?state`

```json
{
  "current_owner": "light_sensor",
  "button":       { "applied": true, "holding": true, "remaining_sec": 135 },
  "light_sensor": { "value": 1234, "is_dark": true, "applied": true },
  "schedule":     { "applied": true }
}
```

- `current_owner` — имя автоматики, которая сейчас держит ленту; `""` — никто (или включён ручной режим).
- Секции `button`/`light_sensor`/`schedule` есть, если для автоматики есть конфиг в NVS
  (в том числе при `is_active: false` — тогда `applied` всегда `false`).
  - `applied` — автоматика сейчас применила своё состояние к ленте.
  - `button.holding` — кнопка держит ленту (нажата и ещё не отпущена таймером или повтором).
  - `button.remaining_sec` — сколько ещё держать, сек; `-1` — до повторного нажатия (`hold: 0`).
    Поля нет, если кнопка ленту не держит.
  - `value` — последнее значение АЦП датчика света, `is_dark` — текущее решение «темно».

## `POST /api/device`

Сохраняет конфиги автоматик в NVS и перезагружает устройство (даже если ничего не изменилось).
Если запись в NVS не удалась — ответ с ошибкой, **без** перезагрузки.

Каждая секция хранится одним JSON-blob'ом (`nvs_set_blob`): у строки в NVS лимит 4000 байт, а полное
расписание (7 дней × 5 интервалов) — около 5,2 КБ. Значения, записанные старыми прошивками строкой,
читаются и при следующем сохранении перезаписываются blob'ом.
Каждая секция опциональна; объект сохраняется целиком, без слияния со старым.

```json
{
  "button": {
    "is_active": true,                      // опционально, по умолчанию true
    "priority": 100,                       // 0..255, выше — главнее
    "action": {
      "hold": 180,                         // сек, сколько держать; 0 — до повторного нажатия
      "repeat": "extend",                  // нажатие во время работы: "extend" | "release"
      "time": {                            // окно активности (опционально)
        "start": { "hour": 19, "minute": 0 },
        "end":   { "hour": 8,  "minute": 0 }
      },
      "led": {
        "mode": 254, "speed": 100, "brightness": 100,
        "color": { "r": 255, "g": 255, "b": 255 }
      }
    }
  },
  "light_sensor": {
    "is_active": true,
    "priority": 20,
    "action": {
      "dark":  300,                        // порог АЦП «стало темно»
      "light": 800,                        // порог АЦП «стало светло»
      "time": {
        "start": { "hour": 18, "minute": 0 },
        "end":   { "hour": 8,  "minute": 0 }
      },
      "led": {
        "mode": 254, "speed": 100, "brightness": 80,
        "color": { "r": 255, "g": 180, "b": 80 }
      }
    }
  },
  "schedule": {
    "is_active": true,
    "priority": 15,                         // 0..255; дефолт 15
    "days": [                               // до 7 дней; day: 0=вс, 1=пн, ..., 6=сб
      {
        "day": 1,                           // понедельник
        "intervals": [                      // до 5 интервалов на день
          {
            "start": { "hour": 10, "minute": 0 },
            "stop":  { "hour": 15, "minute": 0 },   // stop<start = через полночь
            "led": {
              "mode": 3, "speed": 100, "brightness": 80,
              "color": { "r": 255, "g": 100, "b": 50 }
            }
          },
          {
            "start": { "hour": 22, "minute": 0 },
            "stop":  { "hour": 6,  "minute": 0 },
            "led": {
              "mode": 255                   // погасить ленту на ночь
            }
          }
        ]
      }
    ]
  }
}
```

Парсинг — `i_button::from_json` / `i_light_sensor::from_json` / `i_schedule::from_json`.
Невалидные поля молча игнорируются (остаются значения по умолчанию).
`speed` и `brightness` — **0..100** (контроллер игнорирует значения > 100);
Чтобы интервал расписания гасил ленту — `mode: 255`. Для совместимости `mode: 0` и интервал без `led`
тоже превращаются в 255 (эффекта с id 0 нет: без этого лента просто застыла бы на последнем кадре).

Расписание опрашивает текущее время раз в 15 секунд. Если время не синхронизировано по SNTP —
расписание не работает. На каждом такте расписание заново запрашивает ленту (`engage`) и пишет на неё только
пока владеет ею: кнопка с бóльшим приоритетом или ручной режим расписание не перетирает,
а после них оно забирает ленту обратно на ближайшем такте. Вне интервалов расписание ленту не держит (лента в это время находится
в том состоянии, в котором была до захвата расписанием, или в последнем состоянии от ручного
режима / другой автоматики).

### Кнопка: `hold` и `repeat`

`repeat` — что делает нажатие, пока кнопка держит ленту:

| `repeat` | Поведение |
|---|---|
| `"extend"` (по умолчанию, и если поля нет) | Отсчёт `hold` запускается заново (время не прибавляется) |
| `"release"` | Кнопка отпускает ленту: возвращается то, что было до нажатия (режим, цвет, яркость), а не «выключено» |

- `hold: 0` — держать ленту, пока кнопку не нажмут ещё раз. Работает только с `"release"`:
  при `hold: 0` и `"extend"` прошивка сама использует `"release"` (иначе ленту не отпустить никогда).
- Повтор с `"release"` срабатывает и вне окна `time`, и при `is_active: false` — отпустить ленту можно всегда.
- Повтор быстрее 0,5 с после включения игнорируется — защита от случайного двойного клика.
- Неизвестное значение `repeat` → `"extend"` и предупреждение в логе.

### `is_active` — отключение без удаления

У каждой автоматики (`button` / `light_sensor` / `schedule`) есть булево поле
`"is_active": true|false` (опционально, дефолт `true`). При `false`:
- конфиг остаётся в NVS как есть — удалять ничего не надо;
- источник не зовёт `engage()`: нажатия кнопки игнорируются, опрос датчика не реагирует,
  расписание не включает ленту;
- если источник в этот момент владел лентой — он форсированно вызывает `release()`
  на ближайшем такте (для датчика и расписания — сразу; для кнопки — по истечении `hold`).

Изменение `is_active` применяется после перезагрузки (как и весь конфиг).

### Ответы

| Код | Тело |
|-----|------|
| 200 | `{"status": true}`, затем ребут через ~1 с |
| 200 | `{"status": false, "error": "nvs write failed: <секция>"}` — не записалось, ребута нет |
| 400 | см. «Тело POST» |

## `POST /api/network`

```json
{ "mode": "sta", "sta": { "sta_ssid": "MyWiFi", "sta_password": "qwerty123" } }
{ "mode": "ap",  "ap":  { "ap_ssid":  "webled", "ap_password":  "12345678"  } }
{ "mdns": "kitchen" }
```

`mdns` можно передать отдельно или вместе с `mode`. Имя: 1–15 символов `a-z 0-9 - _`, суффикс `.local`
срезается. Применяется сразу (`mdns_hostname_set`), без перезагрузки.

| Код | Тело |
|-----|------|
| 200 | `{"status": true, "success": "sta mode set"}` / `"ap mode set"`, ребут через ~1 с |
| 200 | `{"status": true, "success": "mdns set"}` — пришло только `mdns`, ребута нет |
| 200 | `{"status": false, "error": "mdns: 1..15 chars, a-z 0-9 - _"}` — недопустимое имя |
| 200 | `{"status": false, "error": "invalid mode"}` — `mode` не `sta`/`ap` |
| 200 | `{"status": false, "error": "fail parse json"}` — нет полей / не строки / `set_sta`/`set_ap` вернул ошибку (текст недостоверен, причину смотрите в логе) |
| 400 | см. «Тело POST» |

## `POST /api/file`

Компилирует скрипт и, **только если компиляция прошла**, сохраняет файл в ФС. Ответ приходит после
компиляции (она синхронная). Успешный скрипт сразу появляется в `modes` (`GET /api/led`) с указанным `id`.

```json
{
  "name": "fire",           // имя файла, непустое, без '/'
  "text": "<исходник>",     // текст скрипта, непустой
  "id": 10,                 // id эффекта (0..255); 1..9 и 253..255 заняты встроенными
  "continuous": true        // эффект анимированный (вызывается постоянно)
}
```

Проверки при компиляции:
- синтаксис (`compile: <текст ошибки wrench>`);
- верхний уровень скрипта должен **завершиться**: бесконечный цикл вне `step()` прерывается
  по лимиту инструкций и даёт ошибку `top-level code did not finish (infinite loop?)`;
- в скрипте должна быть функция `step()`.

Каждая ошибка также пишется в лог (`W ScriptEngine: script '<name>' id=<id>: ...`) — и при сохранении
из веба, и при загрузке скриптов на старте.

| Код | Тело |
|-----|------|
| 200 | `{"status": true, "registered": true}` — скомпилирован, сохранён, уже доступен как режим |
| 200 | `{"status": true, "registered": false, "warning": "..."}` — пересохранили скрипт с тем же `name` и `id`: новая версия проверена и сохранена, но эффект заменится **после перезагрузки** (замены на лету пока нет) |
| 200 | `{"status": false, "error": "compile: ..."}` и другие ошибки компиляции — файл **не** сохранён |
| 200 | `{"status": false, "error": "id 10 already in use"}` — id занят встроенным эффектом или другим скриптом |
| 200 | `{"status": false, "error": "name: ..."}` / `"text: ..."` / `"id: ..."` / `"continuous: ..."` — неверное поле |
| 200 | `{"status": false, "error": "file write failed"}` — скрипт скомпилирован, но файл не записался |
| 400 | см. «Тело POST» |

> `DELETE /api/file` удаляет только файл: эффект остаётся в `modes` до перезагрузки.

## Что стоит знать

- **mDNS** и **имя точки доступа** — см. [Имена устройства](#имена-устройства).
- **Запасная точка доступа**: если в режиме клиента за 30 с не удалось подключиться к роутеру,
  поднимается точка с тем же именем и паролем, что и обычная (`webled00001`). В NVS ничего не
  пишется — после перезагрузки устройство снова пробует подключиться к роутеру (`wifimanager::start_ap`).
- **CORS**: заголовков нет. Тестовая страница отдаётся с самого ESP (`GET /`), поэтому CORS ей не нужен.
- **Аутентификации нет** — любой в сети может менять настройки и перепрошивать.
- Исходный проект автоматики (с отличиями от реализации) — [docs/automation-architecture.md](automation-architecture.md).

## Имена устройства

Имя точки доступа (`ap_ssid`) и mDNS-имя (`mdns`) начинаются с одного префикса `webled` и строятся из серийного номера в разделе `meta`
(прошивается `components/device_manager/provision.py`). Из серийника берутся цифры: `SN-00001` → `00001`;
если цифр нет — буквы и цифры в нижнем регистре. Код — `wifimanager.cpp` (`serial_suffix`,
`default_ap_name`, `default_mdns_name`).

| | Без серийника | С серийником `SN-00001` |
|---|---|---|
| Точка доступа | `webled` + 3 последних байта MAC, например `webled41AA94` | `webled00001` |
| mDNS | `webled.local` | `webled00001.local` |

### Как это работает по запускам

Серийник прошивается **после** прошивки и первого запуска, поэтому имена переписываются отдельным шагом:

1. **Первый запуск** (в NVS ещё нет настроек Wi-Fi): точка доступа — по MAC, mDNS — `webled`.
   Оба имени записываются в NVS.
2. **Запуск после прошивки серийника**: если в NVS лежит автоматическое имя (точка — по MAC,
   mDNS — `webled`), оно **один раз** заменяется на имя с серийником и сохраняется.
3. **Все следующие запуски**: в NVS уже имена с серийником, условие замены не выполняется — во флеш
   ничего не пишется.

Без серийника имена остаются автоматическими и тоже не перезаписываются на каждом запуске.

Имя, заданное пользователем (`POST /api/network` с `ap` или `mdns`), не совпадает с автоматическим
и никогда не заменяется. Исключение — если пользователь вручную задал ровно автоматическое имя (по MAC или `webled`):
при наличии серийника оно будет заменено, как автоматическое.

После переименования точка доступа поднимается с новым именем — к старой сети подключиться уже нельзя.
